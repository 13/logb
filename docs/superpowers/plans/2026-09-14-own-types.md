# Own Types Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Each user can create their own object types (name, icon, entry categories, default counter unit) and use them everywhere a built-in type works.

**Architecture:** A per-user `object_types` table synced as a new entity; objects reference a custom type as `custom:<client_uuid>` in the existing `type` column, whose `CHECK` constraint is replaced by one server-side validity function. The frontend resolves every type key through one store (`type-registry.ts`) that knows built-in and custom types.

**Tech Stack:** Rust (axum, sqlx `Any` on SQLite + PostgreSQL), Svelte 5 runes, TypeScript, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-09-14-own-types-design.md`
**Builds on:** objects list and tags projects, both merged first.

## Global Constraints

- Work on branch `build-own-types` created from `main` after the tags project is merged; never commit to `main`. Before every commit run `git branch --show-current` and commit only if it prints `build-own-types`.
- A custom type's key is `custom:<client_uuid>`; `client_uuid` is a lowercase canonical UUID (use the normaliser objects already use for `client_uuid`).
- Name: 1–40 characters after trimming (count characters), unique among the user's non-deleted types ignoring case and accents. Icon: one of the frontend `IconName` values; the server keeps its own list `CUSTOM_TYPE_ICONS` (copy the union from `frontend/src/lib/Icon.svelte`, minus UI-only icons `back`, `settings`, `search`, `edit`, `repeat`, `plus`, `palette`, `person`, `key`, `people`, `database`, `chevron`, `logout`, `bell`, `chart`), and a Vitest test asserts every server icon is a valid `IconName`. Categories: non-empty subset of the activity categories; `other` always present (added if missing). Counter unit: null, `km`, `mi`, `h`.
- Types are per user. Built-in types are unchanged and cannot be edited or deleted. Reminder templates stay built-in only.
- Deleting a type used by any non-deleted object: 409 with `{"error":"in_use","count":N}` (use the error shape `AppError` already produces for 409s; add a variant only if none carries a count).
- Migrations: SQLite next free number (e.g. `0014_own_types.sql`), PostgreSQL next free number (e.g. `0005_own_types.sql`). The SQLite `CHECK` removal follows `migrations/sqlite/0009_object_types.sql`'s rebuild recipe exactly (no-transaction header first line, foreign keys off, create-copy-drop-rename, column order preserved incl. `tags` from the tags project).
- Sync compatibility note (write it into `docs/superpowers/specs/2026-09-08-offline-sync-design.md` under a dated "Later additions" heading): the snapshot gains an `object_types` array and `objects.type` may be `custom:<uuid>`; clients must ignore unknown snapshot keys and treat an unknown type key as "other" for display.
- Portable SQL; Playwright with project defaults; foreground commands (timeouts up to 600000 ms); never weaken an assertion; comments explain *why*.

### Task 2: Sync, export and statistics know own types

**Files:**
- Modify: `src/sync/mod.rs`, `src/sync/apply.rs`, `src/sync/record.rs`, `src/sync/feed.rs`, `src/api/export.rs`, `src/api/stats.rs` only if needed, `tests/sync.rs`, `tests/export.rs`, `tests/stats.rs`, `docs/superpowers/specs/2026-09-08-offline-sync-design.md`

**Interfaces:**
- Sync: `Entity::ObjectType` (`"object_type"`, table `object_types`), whitelist `name`, `icon`, `categories`, `counter_unit` (Text). Create ops carry all four plus `client_uuid`; set ops validate through `domain::custom_type::normalize` (building the full `TypeInput` from the stored row plus the changed field); delete ops refuse (op rejected with reason "in use") while objects use the type. Object create/set of `type` in sync uses `is_valid_for_user`, which must see a type created earlier in the same push (ops apply in order inside one transaction — verify and test).
- Feed snapshot gains `"object_types"` (the user's non-deleted rows); the change feed logs type creates/sets/deletes like other entities.
- Export: top-level `types: [{ client_uuid, name, icon, categories, counter_unit }]` (`#[serde(default)]`); objects keep `type` as exported (`custom:<uuid>`). Import creates types first, remapping to fresh `client_uuid`s when the archive's uuid already exists for another row, and rewrites objects' `custom:` keys accordingly; an unknown `custom:` key in an archive falls back to `other` with the original key appended to the description via the existing `join_unmapped` idiom.
