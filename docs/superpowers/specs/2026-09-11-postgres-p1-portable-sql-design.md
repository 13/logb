# PostgreSQL, part 1: one code path, two databases

Status: approved design, not yet implemented. First of five; nothing here is user-visible.

## Problem

`LogB` is welded to SQLite. `src/state.rs:9` holds a `SqlitePool`, so every handler signature
carries the driver; 135 hand-written statements assume SQLite's dialect; nine migrations use
`AUTOINCREMENT`, `PRAGMA`, `randomblob()` and `COLLATE NOCASE`.

The goal is the data living in PostgreSQL, where it can be queried and joined with other
systems. This part makes the code able to speak to either database. Nothing switches yet.

## Scope

The query layer, the schema, and a test suite that runs against both. Selecting the backend is
an environment variable here; the Settings screen is part four.

Out of scope: the sync cursor's ordering guarantee (part two — it is a correctness problem, not
a porting one), copying existing data (part three), Settings (part four), backups (part five).

## Approach

**One code path.** A repository trait with a SQLite and a Postgres implementation would
duplicate all 135 statements and double the cost of every future change. The statements stay
where they are, written in a portable subset, with a thin adapter for what cannot be avoided.

The pool becomes `sqlx::any::AnyPool`, with drivers installed at startup and the URL deciding
the backend. `AnyRow` covers every type this app stores — `i64`, `String`, their `Option`s —
because dates, money and identifiers are already TEXT and INTEGER.

**Placeholders.** Statements are written Postgres-style (`$1`) and need no rewriting at all:
SQLite's parameter syntax includes `$AAAA`, and sqlx binds them positionally, so one style
serves both backends. Verified in this repository before this spec was written -- an insert and
a select with `$1`/`$2` bind correctly on SQLite through sqlx 0.9.

**The rest of the gap**, in full:

| SQLite today | PostgreSQL | Where it is handled |
|---|---|---|
| `AUTOINCREMENT` | `GENERATED BY DEFAULT AS IDENTITY` | schema |
| `hex(randomblob(16))` | — | generated in Rust instead, which removes the dependency |
| seeded rows using `randomblob` | — | the sync epoch is written by the app on first start |
| `LIKE` for case-insensitive search | `ILIKE` | adapter |
| `ORDER BY … COLLATE NOCASE` | `ORDER BY lower(…)` | adapter |
| `PRAGMA foreign_keys` | always enforced | SQLite-only after-connect hook |
| `VACUUM INTO` | — | part five |

**SQLite's pragmas cannot be expressed in a URL.** sqlx 0.9's SQLite URL parser accepts only
`mode`, `cache`, `immutable` and `vfs`, and `AnyPool` connects by URL alone -- so `foreign_keys`,
`journal_mode` and `busy_timeout` are applied by an after-connect hook to every connection the
pool opens. This is the sharpest edge in the port: losing `foreign_keys` raises no error and
fails no test, it just stops `ON DELETE CASCADE` from happening, and the first symptom is an
attachment that outlived the object it belonged to. It gets its own test, asserting a real
cascade rather than the pragma's value.

## Schema

PostgreSQL gets **one consolidated schema file** describing the current shape, not a replay of
nine migrations. The migration history exists to move existing SQLite databases forward; a fresh
PostgreSQL database has nothing to move. Migration `0009`'s table rebuild with foreign keys
disabled has no PostgreSQL equivalent and needs none.

`migrations/` splits into `migrations/sqlite/` (the nine existing files, unchanged) and
`migrations/postgres/` (the consolidated file). The migrator is chosen by backend at startup.

From here on a schema change is written twice. That is the standing cost of this decision, and
it is the reason the test matrix below is not optional.

## Types

Timestamps stay TEXT holding ISO-8601 strings, and money stays INTEGER cents, on both backends.
Converting to `timestamptz` and `numeric` would be more idiomatic PostgreSQL and would change
every comparison, every serialisation and every test in the app. This part is a port, not a
redesign; a later slice can convert types once the port is proven.

Booleans are already INTEGER 0/1 and stay that way, as `SMALLINT`.

## Testing

The suite is the deliverable as much as the code is. 290 tests currently prove the app works on
SQLite, and a port that does not run them against PostgreSQL is an assumption.

- Every integration test runs against both backends, selected by `LOGB_TEST_DATABASE_URL`.
  Unset means SQLite, so a developer with no PostgreSQL keeps the current experience.
- CI gains a job with a PostgreSQL service container running the same suite. Both jobs must
  pass; neither is allowed to be advisory.
- One test asserts the two schemas agree on table and column names, so a migration written for
  one backend and forgotten on the other fails immediately rather than at runtime on somebody's
  instance.
- No placeholder rewrite exists to test. The conversion of the 135 existing statements from
  `?` to `$n` is a one-time edit, and the suite is what proves each bind is still numbered
  correctly.
- **Search returns the same rows on both backends.** SQLite's `LIKE` is case-insensitive for
  ASCII only; PostgreSQL's `ILIKE` follows the server's locale, so `Ölwechsel` and `ölwechsel`
  can match on one and not the other. A test searches for mixed-case and accented terms seeded
  through the real API and asserts identical results, because this is the kind of difference
  that is never noticed until a German user's search quietly stops finding things.

## What this deliberately does not do

No behaviour changes. On SQLite the app is byte-for-byte what it was, and the 290 tests prove
it. On PostgreSQL it starts, serves and passes the same suite — with the sync cursor's ordering
still unproven, which is why part two exists before anyone points a phone at it.
